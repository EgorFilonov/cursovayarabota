# Правила работы над проектом

Соглашения по коду и процессу для курсовой «Обувной магазин». Документ нужен мне самому и его можно показать как пример того, как в проекте договариваются о стиле.

Проект на Python. Стиль кода — PEP 8, проверка — Ruff. Это замена договорённостям C# и StyleCop из общего шаблона задания: здесь нет `this`, XML-комментариев и `.cs`.

Этот issue не закрывается. Его дополняют по ходу работы. В pull request для него нельзя писать `Fixes`, `Closes` и `Resolves`.

## 1. Стиль именования

Имена по [PEP 8](https://peps.python.org/pep-0008/).

| Элемент | Стиль | Пример |
| --- | --- | --- |
| Модуль и пакет | snake_case | `shoe_store` |
| Класс и перечисление | PascalCase | `Shoe`, `ShoeCategory` |
| Функция и метод | snake_case | `create_shoe` |
| Переменная, параметр, атрибут | snake_case | `shoe_id` |
| Непубличный атрибут | префикс `_` | `_connection` |
| Константа модуля | UPPER_CASE | `MAX_NAME_LENGTH` |
| Первый параметр метода экземпляра | `self` | `def save(self)` |
| Первый параметр метода класса | `cls` | `def create(cls)` |

Дополнительно:

- Аббревиатуры пишутся как обычные слова: `shoe_id`, `api_url`, а не `shoe_ID`.
- Логические имена начинаются с `is_`, `has_` или `can_`: `is_available`.
- Венгерская нотация не используется.
- Однобуквенные имена только у счётчиков циклов (`i`, `j`).
- Имена в коде — на английском. Тексты для пользователя и документы — на русском.
- Импорты тремя группами: стандартная библиотека, сторонние пакеты, модули проекта. Между группами пустая строка.

## 2. Параметр `self`

В задании на C# речь идёт о `this`. В Python у метода экземпляра первый параметр всегда называется `self`. Через него читаются атрибуты и вызываются другие методы.

`self` не опускается и не переименовывается. Локальную переменную нельзя называть `self`.

```python
class ShoeRepository:
    def __init__(self, connection: sqlite3.Connection) -> None:
        self._connection = connection

    def get(self, shoe_id: int) -> Shoe | None:
        return self._find(shoe_id)
```

Если параметр совпадает по смыслу с атрибутом, атрибут всё равно пишется через `self`, а параметру дают обычное имя (`shoe_id`, а не `id`, если так яснее).

## 3. Документирование

У публичных модулей, классов и функций есть docstring. Формат — Google style: его понимает Sphinx (расширение Napoleon). По роли это аналог XML-комментариев C# и тегов, которые умеет читать Doxygen.

Обязательно:

- первая строка — что делает объект;
- `Args` — у каждого параметра, кроме `self` и `cls`;
- `Returns` — если функция что-то возвращает;
- `Raises` — если вызывающий код должен обработать исключение.

Пустой docstring и фраза, которая только повторяет имя функции, не подходят. Комментарий `#` ставится там, где без него непонятно, зачем так сделано.

```python
def create_shoe(payload: ShoeCreate) -> Shoe:
    """Добавляет модель обуви в каталог.

    Args:
        payload: Название, бренд, размер, цена и остаток.

    Returns:
        Созданная запись с идентификатором.

    Raises:
        HTTPException: Поля не прошли проверку или запись не сохранилась.
    """
```

Краткое описание эндпоинта FastAPI берётся из docstring и попадает в OpenAPI, то есть на страницу Swagger `/docs`. Если меняется контракт метода, docstring меняется вместе с ним.

## 4. Сообщения коммитов

Формат — [Conventional Commits](https://www.conventionalcommits.org/):

```text
<тип>: <краткое описание>
```

Описание на русском, без точки в конце. Один коммит — одно изменение.

| Тип | Когда |
| --- | --- |
| `feat` | новая возможность |
| `fix` | исправление |
| `docs` | только документация |
| `style` | оформление, поведение то же |
| `refactor` | перестройка без новой возможности и без исправления |
| `test` | тесты |
| `chore` | служебные файлы |
| `ci` | конвейер сборки |
| `build` | зависимости |

Примеры:

```text
feat: добавить создание модели обуви
docs: сопоставить ГОСТ 19 и ГОСТ 34 с файлами репозитория
ci: запускать pytest в GitHub Actions
```

Тело коммита пишется, только если из заголовка неясно, зачем сделано изменение.

## 5. Ветки и pull request

- Основная ветка — `master`. После первого коммита со структурой репозитория прямой push в `master` не делается.
- Каждая задача начинается с issue.
- Ветка от `master` называется `feature/<номер issue>`.
- Результат сдаётся pull request в `master`.
- Ревьюер — [MarinaPaley](https://github.com/MarinaPaley).
- В описании PR есть ссылка на issue (`#123`). Для этого issue закрывающие слова не используются.
- Одна задача — один pull request.
- Перед PR локально проходят `ruff check .` и `pytest`.

## 6. Прочие договорённости

- Документация репозитория (`README`, эти правила) — только Markdown.
- Текст для пояснительной записки ведётся в MS Word и лежит в папке `КР/`, отдельно от кода.
- `.docx` и другие бинарные файлы помечены в `.gitattributes`.
- Секреты и строки подключения в репозиторий не коммитятся. Туда же не попадают `.venv`, `__pycache__` и файл базы SQLite.
- Зависимости перечислены в `requirements.txt`.
- У публичных функций есть аннотации типов.
- Сборка и тесты на GitHub Actions: Python 3.12, Ruff и pytest. Тесты работают на SQLite.
